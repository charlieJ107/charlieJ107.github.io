Cardiff University COMAT GCG Cluster 为研究组提供 GPU 计算、开发工作区和持久存储。持续运行需要把系统应处于什么状态、当前发生了什么，以及维护后如何确认结果联系起来。运维设计围绕这三类问题组织配置、观测和验证证据。

## 可重建配置与运行资源

纳入版本控制的当前 manifests、Helm values 和 operator resources 描述可重建配置。脚本承担前置检查、执行编排与结果验收，将维护步骤及其完成条件联系起来。工作区的动态资源则由 Coder / Terraform 管理，使基础设施配置与工作区生命周期各有明确的管理职责。

文档按当前运行说明、历史证据和未来计划区分。当前说明支持日常判断，历史证据解释已经执行的变更及其结果，计划记录后续意图。这种组织方式让维护者能够判断一段描述的时间与证据属性，也便于在配置变更时同步核对运行说明。

## 从系统指标定位到工作区

Prometheus / Grafana 覆盖 Kubernetes、Ceph、GPU、Coder 和 PostgreSQL 的运行观测。系统指标提供资源与服务状态，工作区用量进一步归属到用户和工作区，为定位资源争用、异常占用及其影响范围提供上下文。

指标的价值在于支撑具体判断。资源使用变化需要结合工作区活动和服务状态解释；采集到数据后，仍需建立症状与原因的联系。定期只读巡检用于发现状态偏差，滚动维护控制变更推进范围，执行后的验收确认预期结果。这些环节构成持续维护的反馈过程。

## 备份覆盖与恢复验证

CloudNativePG 管理 PostgreSQL。备份采用原生 PostgreSQL WAL 与基础备份，并以存放于 Ceph RGW 的逻辑备份补充。两种方式提供不同的恢复材料：基础备份与 WAL 支持数据库状态的恢复链，逻辑备份提供数据库内容的另一种表示。保留互补材料也带来相应的维护与验证成本。

备份设计还要考虑故障域：数据副本的数量与面对同类故障时的独立性是不同问题。评估恢复能力时，需要检查备份、存储和数据库服务之间的依赖，理解同一次故障可能影响哪些恢复材料。

配置验证检查系统定义是否符合预期，备份完整性检查核对备份材料的一致性，恢复能力则需要实际恢复并验收数据与服务的证据。这一区分决定了恢复流程及其验收条件应如何设计。
