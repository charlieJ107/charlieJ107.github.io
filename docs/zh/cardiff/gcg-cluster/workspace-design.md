Cardiff University COMAT GCG Cluster 为研究组提供 GPU 计算、开发工作区和持久存储。研究项目既需要快速进入可用环境，也需要调整依赖、保留数据和安排计算。工作区设计将这些需求拆分为环境、存储与调度三个相互配合的部分，让各自的生命周期有清晰边界。

## 环境的复用与定制

平台以 MicroK8s Kubernetes 承载工作负载，通过 Coder 和 Terraform 管理工作区。预制的 golden images 提供快速开始的环境，Dev Containers 则承载项目需要的定制。前者集中维护常用依赖，后者让项目对自身的软件环境负责；这也决定了维护成本由谁承担、环境准备发生在哪个阶段。

基础镜像由 BuildKit 构建，自定义环境由 Envbuilder 构建。Golden images 使用不可变 digest 锁定具体镜像，工作区引用的环境因而有可追溯的版本依据。镜像更新成为显式选择；项目仍需管理自己的依赖声明和实验代码，才能解释一次运行使用了什么。

## 数据与工作区的不同寿命

存储采用 MicroCeph / CephFS，为工作区分配 SSD 存储，为用户跨工作区的数据分配 HDD 存储。前者随工作区生命周期组织，适合需要较快访问的工作数据；后者以用户为生命周期边界，承接跨工作区保留的个人数据。个人共享卷可由同一用户的多个工作区使用。

这项划分同时表达性能和保留责任：环境可以重建，数据需要按用途选择归属。跨工作区共享减少重复准备，也要求研究者留意并发访问与文件修改。将数据寿命显式化，能让工作区的创建、替换和回收具有可理解的后果。

## GPU 分配与等待成本

共享 GPU 采用 time slicing，适合共同使用计算资源，但不提供显存隔离。同一设备上的工作负载仍需考虑显存竞争，因此共享方式影响的是使用安排，不能据此推断每个工作区拥有独立的显存边界。

独占 GPU 工作区通过 Kueue 的 StrictFIFO 准入。严格的队列顺序使等待规则清楚，同时可能让后续请求随队首请求等待。准入批准后的镜像准备也占用独占资源，所以实际资源成本包含环境准备时间。工作区停止时释放分配的资源，交互工作的便利也带来及时结束占用的责任。

这些决策把环境可追溯性、数据保留和资源公平性放在同一工作区模型中。配置维护、观测与恢复证据的组织方式见[运维设计](/zh/projects/gcg-cluster/docs/operations-design/)，项目背景见[项目概览](/zh/projects/gcg-cluster/)。
